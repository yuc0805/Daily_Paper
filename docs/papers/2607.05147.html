DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation

Cheng, Yu, Shao et al. (DeepSeek) · arXiv 2026 · link · Appears in: LLM

What

DSpark is a speculative-decoding framework for high-concurrency serving. It couples a parallel drafter with a lightweight sequential module so drafted blocks carry within-block dependencies, and it schedules verification length per request from estimated prefix-survival probabilities. Inside DeepSeek-V4's live serving system it accelerates per-user generation by 60 to 85 percent at matched throughput versus the production multi-token-prediction baseline.

Why

Parallel drafters propose many tokens in one forward pass but their later tokens suffer rapid acceptance decay because they lack inter-token dependencies. Worse, indiscriminately verifying long low-quality blocks wastes batch capacity on tokens with high rejection risk, which degrades throughput when many users are served at once. Prior speculative-decoding methods optimize draft speed without accounting for this verification waste under load.

How

DSpark attacks both problems. A semi-autoregressive architecture pairs the parallel backbone with a small sequential head that introduces intra-block dependency modeling, mitigating suffix decay. Confidence-scheduled verification then tailors the verification length for each request based on estimated prefix-survival probabilities and the engine's throughput profile, so compute is not spent verifying tokens likely to be rejected. The result shifts the Pareto frontier of the serving system under strict interactivity constraints.

Solves vs predecessors

DeepSeek-V3's multi-token prediction drafts several tokens in parallel but loses acceptance on later tokens and does not adapt verification to server load. DSpark restores within-block dependency with the sequential head and adds load-aware verification scheduling, fixing the throughput collapse that the parallel-draft baseline shows under high concurrency.

Method vs predecessors

Where the parent works at the model-quality layer (a fixed multi-token-prediction head), DSpark intervenes at the serving-systems layer: it changes how much each request drafts and verifies based on live estimates of survival probability and engine throughput. The technical novelty is treating verification budget as an adaptive, per-request resource rather than a fixed block length.
